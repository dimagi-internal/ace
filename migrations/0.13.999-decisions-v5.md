# decisions.yaml v4 → v5 — provenance and resolution owner

**No data migration is required.** v5 is purely additive. All three new
fields are optional on the permissive read schema, and every one of the 851
decision rows across the 22 existing runs of `spark-facilitator` and
`hh-poverty-targeting` parses unchanged under v5 (verified by replay before
this shipped). Only new writes are held to the stricter rule.

## What changed

### 1. `status` gains `human-decided`

`status` records WHO settled a row. It gains a third value:

| value | meaning |
|---|---|
| `ai-default` | ACE chose. Its standing judgment; a later run may freely decide differently. |
| `human-decided` | A named person ruled during review and `ai-default` holds **their** answer. Requires `decided_by` + `decided_at`. Carries forward as binding. |
| `overridden` | ACE proposed `ai-default` and a human replaced it via the override path, which keeps both values. |

`human-decided` and `overridden` are genuinely different and both are needed.
`overridden` is the point-and-click path: ACE proposed something, a human
picked something else, and the log keeps both. `human-decided` is for a ruling
that arrives as **input** — a review document, an email — before the row was
ever written. There is no ACE proposal to preserve, and inventing a
counterfactual "what ACE would have said" would be fiction.

**Why this exists.** Measured across 22 runs of two opportunities: 31 rows
carried `feedback_ref`, meaning a reviewer demonstrably shaped them. All 31
were stamped `ai-default`. Because `decision-overrides.yaml` is populated from
overridden rows, nothing was ever written to it — the file does not exist on
either opportunity — so the next run bound nothing and re-derived each ruling
from scratch. One reviewer's six rulings were traced forward: two were never
raised again, one came back in four runs with four different phrasings and
eventually lost its `feedback_ref` entirely, and one that had been correctly
recorded as unresolved had quietly become a confident answer two runs later.

### 2. New `resolved_by: ace | external` (required on new writes)

`resolved_by` answers a different question from `status`: not who settled the
row here, but **whose value it ultimately is**.

- `ace` — ACE's judgment to make from the source material (archetype
  selection, verification layers, solicitation type).
- `external` — the real value is fixed later by someone else: a rate
  negotiated in a solicitation response, dates set on contract execution, an
  FLW count set at deployment.

**`resolved_by` is not an escalation path and gates nothing.** ACE still
picks a value, still writes it as `ai-default`, and the run still proceeds
exactly as before on both values. There is deliberately no `needs-human`
status and no `open` status — `skills/pdd-to-work-order/SKILL.md` has always
said `"open"` is not a valid status, and that remains true. The flag exists so
that:

1. a downstream phase does not cite a projection as a settled commitment, and
2. a later run re-deriving a projection differently reads as **expected**
   rather than as drift.

**Why this exists.** `flw-count`, `payment-rate`, `wo-period-of-performance`
and `wo-total-not-to-exceed-usd` produced a different confident-looking answer
on nearly every run of both opportunities. ACE had originally got this right
and had nowhere to put it: hh-poverty run `20260702-1456` wrote
*"Deferred to deployment (Annex B); negotiated via solicitation response"*
**inside the `ai-default` string** on four rows. Prose in a value field is
invisible to every consumer, so within a few runs all four had become
specific numbers.

### 3. `schema_version` union is now derived

`DecisionsLogSchema.schema_version` was a hand-maintained
`z.union([z.literal(3), z.literal(4)])` that duplicated
`SUPPORTED_SCHEMA_VERSIONS`. The two had already drifted, which surfaces as an
opaque `schema_version: Invalid input` thrown from deep inside a write. It is
now derived from the constant.

## For skill authors

Add `resolved_by` to every row you emit — `DecisionRowStrictSchema` rejects a
row without it at the MCP boundary, before any Drive write. Most `wo-*` rows
are `external`; most Phase-1 design rows are `ace`.

Set `status: human-decided` (with `decided_by` and `decided_at`) whenever the
value you are writing came from a person rather than from your own reasoning
— typically alongside a `feedback_ref` pointing at the review record.

## Known issue found while validating, NOT fixed here

`spark-facilitator/20260727-1850/decisions.yaml` fails `DecisionsLogSchema`
on `generated_at` (`2026-07-24 22:31:05.033000+00:00` — space-separated,
not ISO-8601), and its `run_id` says `20260724-1622`, which is its parent
run, not its own folder. Both predate this change: that run was a fork, and
the fork copied the parent's `decisions.yaml` without re-stamping the header.
Worth a separate fix to the fork path.
