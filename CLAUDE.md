# ACE — Agent Guide

ACE (AI Connect Engine) is a Claude Code plugin that orchestrates the ACE lifecycle for Connect opportunities — idea → app build → deploy → LLO management → closeout. It follows the canopy plugin architecture: `agents/` (procedure docs + subagents), `skills/` (`SKILL.md` files, stateless), `mcp/` (external-system access).

## Agent topology

ACE's nodes come in two forms, and the difference is what they cost in **dispatch
depth**: an `inline` procedure doc is read and executed in its caller's context
(costs nothing, but inflates that context), while a `subagent` is dispatched via
`Agent(...)` and descends one level. Both live under `agents/`.

**This used to be a binary rule and is now a budget.** For most of 2026 Claude Code
withheld the `Agent` tool from every subagent, so anything that dispatched further
work *had* to run at level 0 — that is why the orchestrator and six other nodes are
procedure docs. Nesting landed in **v2.1.172** (depth 5, un-tunable), was defaulted
back to 1 in **v2.1.217**, and settled at **3** in **v2.1.219**. Subagents can now
spawn subagents, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` sets the limit, and
`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20) caps simultaneous fan-out.

> drifted, which is why the topology is now machine-checked.

**Current depth: 2, budget: 3.** The deepest chain is
`ace-orchestrator → synthetic-data-and-workflows → canopy:ddd → canopy:visual-judge`;
the two inline hops cost nothing, so the DDD loop sits at level 1 and its per-scene
judges at level 2. `lib/agent-depth.ts` declares the graph and computes this;
`test/lib/agent-depth.test.ts` fails CI if a chain outgrows the budget, if an
`Agent(...)` target appears in the repo without being counted, or if an inline node
stops justifying its inline-ness.

**Read the depth number before restructuring, and note the failure mode inverted.**
The old rule failed loudly — a level-2 dispatch errored, which is how the Nova
migration regression surfaced. Now, at the limit, Claude Code *withholds* the
`Agent` tool and the subagent at the floor does the delegated work itself and
returns one summary. Nothing errors. `ddd-concept-eval` dispatches
`canopy:visual-judge` as a deliberately *fresh* subagent per scene — its rubric
docks every dimension by 1 if that independence isn't real — so a collapsed
fan-out still emits a full set of verdicts, just correlated and optimistic. Same
shape as the self-graded evals in dimagi-internal/ace#1203, and invisible in every
artifact ACE writes.

So: the inline nodes are no longer *required* to be inline. Lifting
`ace-orchestrator` into a real subagent is now legal (it would take the deepest
chain to exactly 3) and buys real context isolation for a 10-phase run. It also
leaves **zero headroom** — one more nesting level anywhere below it degrades
silently. Before doing it, check whether the DDD specialist fixers
(`/design-review`, `/review`, `/qa`) dispatch anything of their own, and pin
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` explicitly in `settings.json` rather than
inheriting a default that has moved three times this year.

## Phases (current pipeline)

1. idea-to-design → 2. scenarios-and-acceptance → 3. commcare-setup → 4. connect-setup → 5. ocs-setup → 6. qa-and-training → 7. synthetic-data-and-workflows → 8. solicitation-management → 9. execution-management → 10. closeout.

Phases 1–7 run end-to-end with zero LLO involvement. Phase 8 publishes a public solicitation (and emails PDD-named candidates if any). Phase 9 is the first 1-1 LLO contact, gated on `phases.solicitation-management.products.selected_llo.org_slug` in the current run's `run_state.yaml`. Phase 6 splits shallow (in `/ace:run`, ~5 LLM judges) vs deep (out-of-band via `/ace:qa-deep`, ~90 judges); `llo-launch` requires fresh deep verdicts. `app-multimedia-coverage` is a manual post-Phase-3 step invoked via `/ace:step`.

Phase 1 produces the PDD (the formal design doc). Phase 2 derives test prompts (Q&A scenarios for OCS deep QA in Phase 5) and expected app journeys (UX-intent scenarios for app QA in Phase 6) from the approved PDD — both are AI interpretations of an AI-authored PDD, not ground truth.

## Agent operating model — turns, gating, email

ACE is a fleet agent on canopy's agent operating model (spec: `docs/superpowers/specs/2026-07-01-agent-operating-model-adoption.md`; identity: `persona.md` + `config/agent.json`, mailbox `ace@dimagi-ai.com`). `/ace:turn` (level 0, sibling of `/ace:run`) processes inbound surfaces: preflight → canopy-web board drain (config-gated, best-effort — the ace-web vs canopy-web question is deliberately open) → inbox triage → skill self-check → close. Key contracts:

- **Hooks are rails, not approval gates** (Jon, 2026-07-01). `hooks/gating_guard.py` (PreToolUse on `Bash`, plugin-level — fires in every session with ACE installed; rules in `config/gating.json` stay NARROW) carries **deny rails only**: raw `gog gmail send|reply` under the ACE identity is hard-blocked with a message naming `bin/ace-email` (the only send path). The `approve` list is deliberately empty — interactive "ask" prompts stall autonomous runs (the hal lesson); approvals are procedural instead (pause-point mode matrix in `run_state.yaml`, `solicitation-review`'s HITL checkpoint, review posture in turns). Don't add ask rules; encode a new invariant as a deny rail + a procedural gate.
- **`bin/ace-email` / `bin/ace-mark-read` are thin shims over the shared canopy email engine** (canopy ≥ 0.2.255; identity from `config/agent.json`, fixes propagate fleet-wide — ace#826). HTML wrapper, `--reply-all` derivation, timeouts, and keychain-free mark-read are all engine-side; the canopy CLI must be on PATH (`/canopy:setup`). Never reimplement send/mark-read locally.
- **Every send records `thread_id` in the run's comms-log** (`email-communicator` step 7). That's the routing key: `inbox-triage` resolves inbound threads to opp/run by comms-log match, then subject conventions, else unroutable → read-only escalate.
- **Counterpart tiers:** **act** = `config/allowlist.txt` (internal staff; may steer runs), **correspond** = derived from the routed run's state (external LLO contacts; approval-gated replies only, never run mutations), unknown = read-only. One thread, one sender, one memory scope per triage step.
- **Turn state lives in Drive** (comms-logs + `run_state.yaml`), never locally — skills stay stateless; a routed thread always resolves to the opp's current run (run independence holds inside turns).
- `bin/ace-mark-read` clears UNREAD after a thread is fully handled (reading via API doesn't clear the flag). It shells out to `gog gmail thread modify --remove UNREAD` — never mint Gmail tokens via the macOS Keychain `security` call, which hangs forever on a GUI prompt in non-interactive shells (jjackson/ace#827).
- **Reading email — canonical forms, don't re-derive them.** `canopy email read <threadId>` (structured, preferred); to find threads: `gog gmail search "<query>" -a $ACE_GMAIL_ACCOUNT --client canopy --max N -j`; raw thread: `gog gmail thread get <threadId> -a $ACE_GMAIL_ACCOUNT --client canopy --full`. **The gog client is the SHARED fleet client `canopy`, not `ace`** — same as eva/hal/ada; what's per-agent is the mailbox (`-a`). `config/agent.json`'s `gog_client` is authoritative. Do NOT spell it `$ACE_GMAIL_CLIENT`: that var still resolves to `ace` from 1Password, no `credentials-ace.json` exists, and every call fails "OAuth client credentials missing" with a remedy (`gog login --client ace`) that is an interactive browser OAuth a headless turn can't run (jjackson/ace#1147 — clear the var's residual with a vault edit + `/ace:setup --force-env`). The flag is `--max` (there is no `--limit`), search/thread-get need `-a <account>`, and **there is no `message get` subcommand** (`messages` only has `search`/`modify` — read a single message via its thread). Measured 2026-07-28..30: six sessions each burned ~5–10 calls rediscovering exactly this.
- Reply quality follows canopy's operating-model **§1b checklist** by reference (deliverables are gdocs + draft inline; decide-then-show numbered; verify recipients from the structured read); inbox noise classes and open-thread aging (>5 days → escalate to the run's operator) are standing rules in `skills/inbox-triage`.

## Git worktrees and merging to main

This repo uses emdash. If you're in a worktree (`git rev-parse --git-dir` contains `/worktrees/`), the `main` branch is checked out in a sibling worktree — typically `~/emdash/repositories/ace/` or `~/emdash/worktrees/ace/emdash/<some-branch>` whose tip is the latest merge to main. Run `git worktree list` from any worktree to find the exact path on this machine. You CANNOT `git checkout main` from a worktree that doesn't already have it.

**`main` is branch-protected** (`clean-install` status check required) — direct push is rejected. Ship via PR: `bash scripts/version-bump.sh`, commit, `git push -u origin <branch>`, `gh pr create`, then arm auto-merge with `gh pr merge <pr> --auto --merge`. The PR lands itself once `clean-install` passes (no manual review gate). Wait for the merge to land, then run `/ace:update` + `/reload-plugins` in this session.

Version-collision recipe (multiple worktrees bumped in parallel — common): `bash scripts/version-bump.sh --rebase-first` then `git push --force-with-lease`. The flag fetches origin/main, rebases, auto-resolves conflicts in the 4 version files (`--ours`), then recomputes the next version against the freshly-rebased base. Aborts cleanly if any non-version-file conflict surfaces (those need human review).

## Plugin updates — NEVER locally patch

**CRITICAL: Never copy, rsync, or write files into `~/.claude/plugins/cache/` or edit `~/.claude/plugins/installed_plugins.json` by hand.** Local patching bypasses the plugin system, creates version mismatches, and makes bugs hard to diagnose. If you feel the urge, STOP — use `/ace:update` instead.

### Update workflow (the ONLY way)
1. Make changes in the repo.
2. Bump version. **Recommended (worktree-safe):** run `scripts/version-bump.sh` — fetches `origin/main` and picks `max(local, origin) + patch+1`, writing all 4 files atomically. Removes the deterministic VERSION/plugin.json/marketplace.json/package.json rebase conflict that hits when several worktrees bump in parallel. Manual fallback: edit `VERSION` only; pre-commit hook syncs `package.json`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`.
3. Commit on the worktree branch, push, open a PR, arm auto-merge with `gh pr merge <pr> --auto --merge` (or check the auto-merge box in the PR UI). The PR lands itself once `clean-install` passes — no manual review gate. (`main` is branch-protected — direct push is rejected.) See § Git worktrees and merging to main for the canonical block, including the version-collision rebase recipe.
4. **IMMEDIATELY after the PR merges**, run `/ace:update` in the current session. Mandatory — without it, this session runs stale code while new sessions get the bump on startup. (Auto-merge means the merge is asynchronous; watch with `gh pr view <pr> --json state,mergedAt` or `gh run watch` if you need to block.)

**Inside a live `/ace:run`, "immediately" means "at the next phase boundary."** Standing operator directive (Jon, 2026-08-18): *"`/ace:run` should always try to be the most up to date; we are always improving ACE."* A long run that finishes on code we already knew was wrong spends hours proving a stale premise. The phase boundary is the whole safety margin — no phase is in flight there, so nothing hot-swaps under a running skill. Never update mid-phase, and never kill a phase in flight to take an update: `qa-and-training` consumes a one-way precondition (Learn completion is one-way per `(test user, opportunity)`), so an interrupted walk needs a fresh opportunity and therefore a fresh Phase 4. The orchestrator re-checks currency at every boundary — `agents/ace-orchestrator.md § Plugin currency at the boundary`. Superseded the contradicting "the run does not consume its own fix" rule (ace#1500).

**Three actions, only one of which is `/ace:update`.** `/ace:update` writes the disk + registry, so subsequent `Skill()` loads resolve to the new `installPath`. `/reload-plugins` re-reads skills/agents/commands/hooks that are already bound. **Only a full Claude Code restart respawns MCP subprocesses.** Do not report an update as having fixed a stale MCP child — see § MCP changes need a full Claude restart, and note that `mcp/mobile/recipes/*.yaml` are re-read per call from *the version directory the subprocess was launched from*, not from whatever is newest on disk.

**Shipping a change, or dispatching a fix-and-ship subagent?** Use `skills/shipping` — it owns the mechanics (bump → PR → wait → merge → verify → the unconditional ship checkpoint), and `agents/orchestrator-reference.md § Fix-and-ship subagent template` is the dispatch wrapper over it. **Never hand-roll the wait:** a foreground `sleep` used to wait is blocked by the harness Bash contract, and the fallback burns the full 10-min timeout (`Exit code 143`) on a PR that merges in ~70s. Returning before the merge confirms is the #1 source of "PR queued but actually stuck" handoffs.

Hook setup if needed: `git config core.hooksPath scripts/hooks`. Two hooks ship: `pre-commit` (syncs VERSION → JSON when VERSION is staged) and `pre-push` (refuses direct pushes to `main` — server-side protection already blocks them, but this catches muscle-memory pushes before the roundtrip; bypass with `git push --no-verify` if ever needed).

Cache dir is keyed by version: `~/.claude/plugins/cache/ace/ace/<version>/`. On session start, Claude Code pulls the marketplace repo, compares `plugin.json` version against the installed version, and re-installs if different.

### MCP changes need a full Claude restart (not just `/reload-plugins`)

Editing MCP code in `mcp/` (or a new schema deploying upstream — e.g. labs publishes a new `tools/list`) does NOT take effect in the current Claude Code session via `/ace:update` + `/reload-plugins` alone. **MCP subprocesses bind their tool list, schemas, and module code at subprocess startup** — that's tied to the parent Claude Code process, not to plugin reloads. After:

- Editing anything under `mcp/` (atom handlers, capability maps, backend wiring, `tools/list` shape) and merging the change
- An upstream MCP server (labs, OCS, Connect) deploying a new schema while your session was running
- `/ace:update` bumping the plugin to a version whose MCP code differs
- **`/ace:setup --force-env`, or any other `.env` rewrite.** Same mechanism, different trigger: every MCP server calls `dotenvConfig()` at module top level (`mcp/connect-server.ts:18`) and consumes the result at import (`buildHqClusterRegistry` at `:62`), so a subprocess spawned *before* the write holds the old values for its whole life. **Run setup FIRST, restart AFTER** — the reverse order silently keeps the stale env, and nothing else surfaces it. Measured (ace#880): connect MCP up at 21:17:09, `.env` written 21:17:54 → the HQ cluster registry read `[us]` while the file on disk yielded `[eu, us]`, and the parser was correct the whole time. *Enforced:* `/ace:doctor`'s `env_freshness` probe compares each MCP child's start time against `.env`'s mtime and names the stale pids (`lib/env-freshness.ts` + `test/lib/env-freshness.test.ts`); `bin/ace-setup` prints the restart banner on every write. Seen once and not reproducible since: a worktree-rooted MCP survived a full app restart — if `env_freshness` still warns after quitting, `kill` the pid it names.

…the running MCP subprocess is still holding the OLD code/schema. `/reload-plugins` reloads agents + skills + hooks; it does NOT respawn MCP subprocesses. **Quit and reopen Claude Code (full process restart)** to pick up the new MCP behavior.

Symptom of skipping this: payloads that match the documented schema get `INVALID_SCHEMA` rejections; new atoms don't appear in `ToolSearch`; deprecated atoms still resolve. The on-disk code is right; the running subprocess is just stale. (Seen live on the `solicitation-create` schema-drift class, where ACE read a pre-PR-#211 `{data: {...}}` shape weeks after the live schema went flat.)

**Check the running subprocess, not the version files — they cannot see it.** `VERSION` and `installed_plugins.json` are both *on-disk* facts; a session that auto-updated on startup can have rewritten them ~1s AFTER it already spawned its MCP children from the previous version. Both then read correctly while the live code is stale:

```bash
ps -eo ppid,command | awk -v c="$PPID" '$1==c' | grep -o "0\.13\.[0-9]*"
```

`$PPID` inside a Bash tool call IS this session's `claude` pid, so this binds to this session's MCP children and ignores orphans from sibling sessions.

**Caveat — that prints a DIRECTORY NAME, which can lie.** The cache dir is named from `.claude-plugin/plugin.json`, but it's filled from the marketplace clone's HEAD. When those drift the label is wrong: on 2026-07-27 `cache/ace/ace/0.13.667/` contained `0.13.670` code (its own `VERSION` file said so), so the check reported stale code that was actually current. The authoritative read is the version file INSIDE the directory the process is running from:

```bash
cat ~/.claude/plugins/cache/ace/ace/<dir-from-the-check-above>/VERSION
```

Use the `$PPID` check to find WHICH directory the live subprocess uses; use that directory's `VERSION` to learn what code is actually in it. The drift that caused this is gated in CI by `scripts/check-version-unique.ts`, run from **`clean-install`** — `main`'s only REQUIRED check — so a PR whose VERSION is already on `origin/main` cannot merge, and a push to `main` that fails to advance VERSION goes red immediately (ace#1593). It deliberately reads `origin/main` LIVE: `version-check.yml` compares against the PR's captured base sha, which two PRs off one base both satisfy while bumping to the SAME value, and it is advisory anyway — that combination is how 4 of ~20 PRs in one 2026-08-24 sweep shipped duplicate versions, 3 of them unreachable by `/ace:update` until a follow-up bump. Still read the content when it matters. Live case 2026-07-26 (ace#957 validation): both files read `0.13.665` while the running `mobile-server` was `0.13.661` — a whole session nearly went into validating code that was never loaded. Main bumps ~9×/day, so **a fresh session is necessary but not sufficient** — it must have started *after* the update landed. Worth running first in any session that will validate MCP-side behavior.

Nuance worth knowing: **recipes/YAML under `mcp/mobile/recipes/` are re-read from disk per call**, so they can be hot-patched in the plugin cache and take effect immediately. Compiled MCP code cannot — that's what needs the restart. **Hot-patch the directory the `$PPID` check above names, not the newest one:** a live subprocess re-reads recipes from the version directory it was LAUNCHED from, so after an `/ace:update` it keeps serving the OLD version's recipes — faithfully, and with no symptom. That makes this worse than the compiled-code case, which at least fails visibly; here it reads as hot-patchable and silently is not. Measured on bednet-check-2-visit/20260817-1720: a Phase 6 device walk ran against recipes 15 versions stale, five of them changed. See § Update workflow for the boundary-currency policy (ace#1500).

When in doubt, validate by curling the live MCP's `tools/list` directly (e.g. `curl ... https://labs.connect.dimagi.com/mcp/ -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'`) — that response is the canonical contract. If it disagrees with what `ToolSearch` shows you in-session, restart Claude.

## Conventions

- **Skills are stateless.** Per-opportunity state lives in Drive `ACE/<opp-name>/`. Don't introduce local state in `SKILL.md` files.
- **SKILL.md naming.** Skill dir is kebab-case verb phrase (`idea-to-pdd`, `app-test-cases`); must match frontmatter `name:` exactly.
- **MCP servers run direct from TypeScript.** ESM + `npx tsx`, no build step.
- **MCP capabilities are atomic.** Each atom in `mcp/{ocs,connect,mobile}/capability-map.ts` (and `mcp/connect/backends/commcare.ts`) routes to REST or Playwright; skill code never knows which. When upstream ships a real API for a Playwright-backed atom, it's a one-line routing change.
- **VERSION is the single source of truth.** Edit `VERSION` only; pre-commit hook syncs the other files. `/ace:doctor` verifies. Worktree-safe bump: `scripts/version-bump.sh`.
- **Phase Write-Back Contract.** Every phase MUST write `phases.<phase>.{status, verdict, completed_at, summary_artifact, steps}` to `run_state.yaml` on completion (no separate `gates.<gate>` flip step — pause-point status is derived from the phase block + per-skill verdict files). The orchestrator's `classify_phase_writeback` atom is the structural runtime check used by the Phase boundary fence; `validate_run_state` returns the full issue list when the classifier says `'malformed'`. Implementation: `lib/run-state-validator.ts`. See `agents/orchestrator-reference.md § Phase Write-Back Contract`. Without it `/ace:status` misreports, `opp-eval` rollups walk empty, and resume-after-interrupt can't tell which phases shipped.
- **QA vs Eval is a two-phase pattern, calibrated against ground truth.** `*-qa` skills capture transcripts + structural checks; `*-eval` skills judge via LLM-as-Judge with hard-deduction rules and inflation guards, writing per-run `<N>-<phase>/<skill>-eval_verdict[-<mode>].yaml` next to the producer artifacts (no top-level `verdicts/` directory; no `gate-briefs/` — the orchestrator synthesizes pause summaries from verdict files at runtime). Uniform shape so `opp-eval` aggregates any skill. Shallow runs in `/ace:run`; deep runs out-of-band via `/ace:qa-deep`. Per-rubric calibration uses ground-truth catalogues (`ACE/<opp>/eval-calibration/known-issues.md`, opp-level — shared across runs) and multi-run variance protocols.
- **Archetypes are first-class.** PDDs declare `Archetype: atomic-visit | focus-group | multi-stage`; archetype-aware skills branch via `## Archetypes` sections. Adding a new archetype is purely additive (per-skill PRs). Default is `atomic-visit`.
- **Class-level preventers > instance-level fixes.** When a silent-failure class surfaces, catch it at the boundary (MCP backend, doctor probe, schema pre-flight, HTTP probe) so future instances are structurally impossible. Don't just patch the case in front of you. The `ocs_shared_collection_team` doctor probe is the canonical example: a 50ms HTTP request that turns "configured" into "configured correctly."
- **Don't locally reimplement what the shared engine already provides — diagnostics included.** The `bin/ace-email` line above states this for the send path; the class is broader, and the half nobody wrote down is where it bit. `bin/ace-doctor`'s `gog_auth` probe re-derived canopy's `agent_doctor.check_email_auth` by hand as a `grep -qiE` over gog's stdout for known error strings. canopy's version calls `preflight()` and gets a real `(ok, lines)` back; ACE's guessed at another system's error vocabulary and missed `No auth for gmail <mailbox>.` — so a mailbox that could not make a single call reported `PASS gog_auth: live scopes OK` and the turn preflight printed `HEALTHY`. Five counterpart threads then sat unread for 9–22 days (ace#1338). Before writing a check, a shim, or a parser against a surface canopy already wraps, go read what canopy does and call it; a local copy inherits none of the fleet's fixes and none of its tests.
- **Close the loop to the source of truth — don't guess at what another system owns.** When a bug is really "ACE is guessing at a value another system is authoritative about," *observe the real value from that system once* and lock it behind a test — never ship another plausible guess. Two shapes: (1) **live-device truth** — calibrate a selector map / Maestro recipe against a live `mobile_capture_ui_dump` *and run it on-device to confirm it navigates*; don't transcribe from a sibling APK version (the 2.63.0 selector drift, jjackson/ace#591/#593, was copied unverified from 2.62.0 and only caught when Phase 6 burned wall-clock). (2) **contract truth** — get the authoritative answer from the upstream validator/runtime (Nova `validate_app`, Connect budget check) rather than trial-and-erroring values through it (#586's `entity_id` cycled three failing guesses). **When you change recipe/selector logic, validate it live before shipping** — unvalidated branches recreate the class you're fixing. If you can't reach a surface this session, encode what evidence confirms and mark the residual precisely. New-APK-version maps are calibrated against a live device as a first-class step, not discovered wrong in production.
- **When something that WORKED starts failing, read what shipped upstream before concluding it needs a live probe.** ACE integrates with five systems it does not own and they ship continuously (OCS merged 24 PRs in five days around 2026-08-18). The signature is: the call path is unchanged on our side, an older object of the same kind still works, and a new one fails with an opaque error. That is invisible to code reading, so every triage that reads only ACE's code concludes "blocked on a live surface" — and parks a `blocks-e2e` defect behind a visit nobody schedules. `skills/upstream-regression-triage` is the procedure (window → upstream repo → merged PRs → confirm the mechanism in upstream SOURCE, never the PR title). Repo slugs live in its § Process step 3 table; *Enforced:* `test/skills/upstream-repo-slugs.test.ts`, because a wrong slug 404s and an unattended agent reads that as "no upstream changes." Canonical case: ace#1492 — three triages called it blocked while OCS #4202, a public diff, had added `enabled` to `ChannelForm.Meta.fields`; an omitted Django checkbox posts as `False`, so every widget channel ACE created was born disabled while the migration kept existing ones alive.
- **For an external state transition, attempt the transition and treat the conflict as the skip — never let a read-back flag stand in for it.** Call it unconditionally; catch "already done" as the skip signal; branch on the *call result*, not a flag you read. A **cost-skip** (avoids redundant work, re-validated live downstream) is fine; a **correctness-skip** (reads one system's flag and decides not to perform a transition another path depends on) is a footgun — the flag may not mean what you think. Only safe when its guard is the very state the dependent step reads. Sibling of "restore, don't adapt" and "close the loop to the source of truth." Canonical failure: jjackson/ace#624.
- **A guard that PREDICTS another system's rejection must cite a reproducer, or it doesn't ship.** Enforced by `test/skills/predictive-guard-citation.test.ts` (a ratchet: new uncited claims fail CI; the 34 existing ones are a ledger to pay down). The sibling of the rule above — that one says *don't read a flag instead of acting*; this one says *don't predict the failure either*. If a skill asserts an external system `rejects with` / `refuses to` / `silently drops`, it must name the issue, the run id, or the repro that observed it. Canonical failure: ace#1238. `app-hq-settings` refused to patch any form containing a `<case>` block, predicting a `make_build` rejection. It cited a doc that doesn't contain the claim, and the error string appeared exactly once in the repo — inside the guard's own justification. But Nova emits `<case>` inside `__nova_operations` on every app that writes case properties, so it fired on essentially every ACE Deliver app: camera-only was never applied, `app-release-qa` Step 2.8 then halted because it was missing, and **Phase 3 deadlocked on every run**. Nothing in ACE caught it — Jonathan did, by asking. Two more of the same shape landed the same day (`caseWrite` acts as a preload; a visible case-bound field preloads implicitly — both false). A *narrower* scan is still a guess: delete the prediction and let the real call be the authority.
- **File ACE issues mid-run the moment you've confirmed one — don't just narrate.** Navigating around a broken script/recipe/atom to keep a run moving is expected. But once you've *confirmed* a defect or concrete improvement (root cause + how ACE should change), **immediately `gh issue create` against the ACE repo's `origin` (no `-R` needed)** — one issue per finding (title + root cause + run/repro + a "fix lands here: `path`" pointer) — then keep going. Don't defer to run-end (you'll lose the precise repro) or fix-in-place silently (the class-level fix gets lost). Bar: file when you'd bet it's real — false positives are cheap to close, lost findings are not. But "real" is a claim about a **specific defect**, not about a gap: if essentially every ACE capability would carry the same complaint ("X is unvalidated", "nobody has judged Y"), it is a residual, not an issue — ace#1466/#1468, closed by Jon 2026-08-17 as *"this should not have been an issue"*. Scope it to this repo's code/harness too; a defect in one run's Drive artifacts has no durable home here (ace#1395). **Report every issue filed in the run summary.** Pairs with "class-level preventers": the issue is how the preventer gets tracked. **Five things every filing must do** (each added because its absence cost real money):
  1. **Verify the premise against the artifact, and quote what you ran.** If the claim is "X is absent" or "system Y rejects Z", open the file / run the grep / read the doc, and paste the command and its output into the body. Asserting a check you did not perform is the single most expensive filing error: ace#1481 claimed "grep for `MSA` — all zero hits" when the clause sits at `templates/work-order-template.md:147` and in both documents it cited as repro, and a follow-up comment then reported "Confirmed zero hits" on a document containing the string. An unquoted "confirmed" is not a confirmation. Six of the 26 issues closed NOT_PLANNED since 2026-07-18 were false premises (#1128 #1054 #897 #811 #1012 #824). Attempting the self-heal is the cheapest way to run this check — see the self-heal rule below.
  2. **Search first, in its OWN Bash call.** `gh issue list --search "<the failing symbol / file / error>" --state open`, read the hits, *then* decide. #858 and #860 are the *same* defect — same file, same function, same repro, same Nova app IDs — filed three days apart. If a match exists, **comment on it instead** (add your repro; that's strictly more valuable than a second issue), and treat a shared *root cause* as a match too, not just an exact duplicate — 12 of those 26 NOT_PLANNED closes were real findings consolidated into an umbrella (#1022, #1218, #1250). *Enforced:* a `config/gating.json` deny rail blocks search-chained-with-create in one invocation, because that is how the rule kept failing — the create runs before the results can be read (ace#1141, #1052, both self-diagnosed; `test/hooks/gating-guard.test.ts`).
  3. **Label the blast radius**: `--label blocks-e2e` (an `/ace:run` cannot complete), `harness` (ACE's own scaffolding is wrong but a run survives), or `polish`. Without this the tracker can't distinguish "Phase 6 is dead" from "a doc line is stale", so triage sorts by effort and the cheap tier gets all the attention while the blocking tier ages — that's the churn signature, and it's how #811/#824/#796 sat for a month.
  4. **If the issue came from a human's review, stamp it: `Feedback-Ref: <record-slug>/<item-id>`** as a trailer line in the body. That one line is what lets the reviewer see where their comment went (`skills/feedback-ledger`, a DERIVED view — the stamp is the only write-side obligation). An unstamped response renders as **UNROUTED** in their ledger, which is the intended loud failure: it reads as "we ignored you" even when we didn't.
  5. **If the class is testable, land the failing test in the same breath.** The issue tracks the *fix*; a test is what makes the class structurally impossible, and closing an issue deletes its memory while a test keeps it. This is "class-level preventers > instance-level fixes" applied to the filing rule itself. CI was `npm ci` + `npm ls` + `tsc` — no vitest — until 2026-07-25, and in one week #917 and #892's manifest entry both landed **red on main** because nothing ran the suite (PR #952 closed the gap). An issue is not a regression test.
- **Close with the right reason — `COMPLETED` must mean "we actually fixed it."** `gh issue close` defaults to `COMPLETED`, so a tracker where triage closes duplicates and obsolete items with the default reads 203 COMPLETED / 1 NOT_PLANNED and answers *nothing* about how many real defects were eliminated. Use `--reason completed` only when code changed to resolve it; `--reason "not planned"` for duplicates, obsolete, superseded, and wrong-repo. Always cite the `file:line` or the `#n` you're deduping into.
- **Self-heal a filed issue when you can, then close it — don't just file and route around** (Jon, 2026-07-22). *Enforced inside a run:* the Turn N+3 **self-heal sweep** in `agents/ace-orchestrator.md § Phase boundary fence` classifies every issue the phase filed and background-dispatches the self-healable ones via `skills/shipping` — never blocking the run. It became a fence step because as prose it ran at 58% inside live runs vs 71% retrospectively (measured 2026-08-18, 119 issues). Attempting the fix is also the cheapest premise check there is — a self-heal that *refutes* the issue closes it `not planned` and is a success, not a failure. Filing is the floor, not the ceiling. The instant a filed issue is *self-healable* — you understand the root cause AND the fix is bounded, low-risk, and lands in the ACE repo (a recipe/palette/selector/skill/atom edit, a doc/contract fix) — **fix it now: edit → `bash scripts/version-bump.sh` → commit → PR → arm auto-merge (`gh pr merge <n> --auto --merge`) → `gh issue close <n>` referencing the PR → `/ace:update` → then re-run the step that was blocked.** Don't wait for run-end and don't leave a green issue tracking a fix you could have shipped in-session. **Two gates before you merge a self-heal:** (1) **Live-validate a DEVICE-TRUTH claim** — export `ACE_MOBILE_STATIC_RECIPES_DIR=<repo>/mcp/mobile/recipes/static` and restart Claude to run the staged palette without patching the plugin cache (recipe: `playbook/integrations/mobile-integration.md § Validating a palette fix pre-merge`). An unvalidated device-truth fix can reopen the 2.63.0 selector-drift class, so prefer a live re-run of the blocked leg when one is available.

  **This gate is a PREFERENCE, not a blocker — a device-truth fix may merge without a fresh device run, with the residual named in the PR** (Jon, 2026-08-17). The gate was written as "hard" and the cost landed in the wrong place: it does not make bad changes good, it makes *known-good changes sit*. Two measured cases, both found by the 2026-08-17 triage, both stalled for weeks under it:
  - **ace#972** sat behind a "blocked on a live device" comment whose premise was false on the day it was written — the surfaces it named had shipped 16 days earlier. The remaining work was *text*: a recipe header declaring a surface UNVERIFIED that its own sibling recipe had already recorded. Nothing was sent to a device; nothing was matched against one.
  - **ace#1289** (`blocks-e2e`) carried its device evidence **inside the issue body** — the exact budget was run on-device, the scroll and assert COMPLETED, and the Learn leg walked to green. It waited three days for a device it had already visited.

  So, three amendments:
  - **Recorded device evidence IS device evidence.** A transcript in an issue, a run log, or a prior PR satisfies this gate. Re-running a device to re-observe something already observed is not validation, it is ceremony — and a device run is NOISY, so a second flaky green is weaker evidence than the first clean one you already have.
  - **If the residual is nameable, merge and name it.** State in the PR what was not re-observed and what would falsify it. A fix waiting for a device is not safer than a fix merged with a named residual; it is the same risk plus an unfixed defect, and the tracker loses the repro in the meantime.
  - **A stale block is not a block.** Before deferring anything to a device, re-read the premise against current code. Both cases above were blocked on claims that no longer held, and neither was re-checked across two prior triages.

  What has NOT changed: when you are about to *guess* a selector, a coordinate, or a value another system owns, get the real one — that is § "close the loop to the source of truth", and it stands on its own. The device gate was only ever an instrument of it, and it must not outlive its purpose by holding fixes whose truth is already in hand. **The trigger is the CLAIM, not the directory.** Ask: *does this change alter what is sent to, or matched against, the device?* Selector strings and maps, tap coordinates, recipe step ORDER, waits that gate on UI state → **device**. Everything downstream of the device's response — screenshot naming and collection, static probes, parsers, report assembly, watchdog arithmetic → **unit test**, even inside `mcp/mobile/`. Two live cases, same directory, opposite correct answers: ace#1235 (the sanity probe cross-producting modules x forms) is set logic, fixed and proven device-free; ace#1236 (a `/` in a trilingual label scattering screenshots into subdirectories) is filename handling whose ground truth is Maestro's own `Orchestra.class` — a *better* authority than one device run, which tells you what happened once where the source tells you what always happens. A device run is also NOISY, not merely expensive: a flaky green is weak evidence, so mandating one for deterministic logic lowers signal while raising cost. **When you cannot classify it confidently, it is device-truth** — the asymmetry is that under-claiming costs one device run while over-claiming recreates selector drift — and the PR states which class and why, so the call is auditable. But classify-as-device-truth means *prefer a device run and name the residual if you don't get one*; it does not mean *do not merge*. (2) **Scope discipline** — self-heal the surgical fix behind the issue; if the "fix" needs human product/taste judgment, a risky cross-cutting refactor, or you can't validate it this session, leave the issue open and say why. When you self-heal, the run summary reports the issue as *filed + fixed (PR #n, merged)*, not just filed.
- **No inferred backstory.** Skills must work from inputs that exist in `ACE/<opp>/inputs/` or the run state — never invent context (claimed populations, partner relationships, historical pilots) that the source material doesn't contain. PDD drafts that fabricate plausible-sounding details poison every downstream phase. See `docs/learnings/2026-05-12-no-inferred-backstory.md`.

## Phase preconditions are restored, not adapted

Each phase has a known precondition (the state it expects). Recovery is **restore to that precondition**, not **detect-and-adapt to whatever state is in front of us.** Already implicit elsewhere in ACE (run independence; fresh Connect opp per run; fresh OCS chatbot clone per opp; Nova builds from scratch per run). Made explicit after a Phase 6 misstep that introduced state-classification logic instead of restoration.

The pattern:

1. **Precondition declared.** "Phase 6 expects: AVD at Connect home, test user signed in to PersonalID, opp tile reachable."
2. **Restore unconditionally.** Don't probe-first. Don't decide-then-act. Run the restore operation every time. Deterministic starting state, deterministic recovery path.
3. **Verify post-restore.** A classifier earns its keep ONLY as a verification step after restore — if the restore *should* have produced the precondition but didn't, the classifier names which precondition is still violated. That's the only path a classifier is the right tool.
4. **Fail loud.** If restore can't reach the precondition, throw a typed error with the precise class. Don't ship placeholders, don't soft-fail with `verdict: incomplete`.

Canonical implementation: the mobile heal funnel (`mobile_ensure_avd_running`) — **always full cold-boot per dispatch**, never warm-state reuse, ~60-90s steady-state. Full step-by-step (cold-boot sequence, the failure classes it eliminates, the verify-only classifier) + debug-arc context in `playbook/integrations/mobile-integration.md` and `docs/learnings/2026-05-14-phase6-validation-arc.md` (+ `2026-05-14-demo-user-no-otp.md` for the `+7426` demo-user OTP-skip).

The server-side `${ACE_E2E_PHONE}` invite check (CONNECT-ID-3F precondition) is structurally satisfied within `/ace:run` by Phase 4's `connect-opp-setup` running before Phase 6 — no operator action required mid-run.

**Cloud backend equivalent:** `/api/mobile/ensure-running` cold-boots from AMI and runs registration recipes — same contract, different mechanism. The AMI's baked registration scripts produce a fresh demo user on every cold-boot; ace-mobile MCP doesn't have a local snapshot-load that could go stale.

Each phase's heal lives in one place and funnels through the matching `mobile_ensure_avd_running` / `connect_*_setup` / `ocs_*_setup` atom.

**Anti-pattern: tolerance for "whatever starting state we find."** That's complexity in service of a question the phase shouldn't be asking. If you find yourself writing a state-classifier as the primary recovery mechanism, you're solving the wrong problem — flip it to "always restore; classify only on verification failure."

## Auth model: per-machine vs 1Password-backed

ACE has two classes of credential state — confusing them is the #1 source of friction across workstations. Session cookies are bound to TLS fingerprints + CSRF rotation; copying them between machines is *worse* than re-login (intermittent, hard to debug). **Don't sync `~/.ace/` via 1Password or git.**

**1Password-backed (set up once per machine, then static):**
- `${CLAUDE_PLUGIN_DATA}/.env` — every key in `.env.tpl` (most `ACE_*`, `OCS_*`, `CONNECT_*`, `LABS_MCP_TOKEN`, etc.). Source of truth: 1Password vault `Agent-Ace` (ACE's own vault, per the fleet per-agent vault split; the legacy shared `AI-Agents` vault still holds copies but is no longer read). Rotate there and re-run **`/ace:setup --force-env`** (NOT a raw `op inject -o <plugin-data>/.env` — that drops local-only keys like `ACE_WEB_PAT_TOKEN`; `bin/ace-setup` preserves them).
- `${CLAUDE_PLUGIN_DATA}/gws-sa-key.json` — Google SA key. Static (SA keys don't expire).

**Local-only secrets in `.env` (preserved across `op inject`):** `ACE_WEB_PAT_TOKEN` (per-human, minted via `/ace:ace-web-pat-mint`) and any other key not in `.env.tpl`. `bin/ace-setup` snapshots non-template keys before each `op inject` and re-appends them in a marker block (`# --- ACE local-only secrets ...`). Template keys always win — 1P is authoritative for declared keys.

**Per-machine (re-login required per workstation):**
- `~/.ace/ocs-session-<team>.json` — OCS Playwright cookies. Auto-relogin via `OCS_USERNAME/PASSWORD`; manual: `/ace:ocs-login`.
- `~/.ace/connect-session.json` — Connect + CCHQ cookies. Auto-relogin via `ACE_HQ_USERNAME/PASSWORD`; manual: `/ace:connect-login`.
- `~/.ace/playwright-userdata/` — chromium profile for Connect probes. Re-seed via `scripts/seed-connect-cookies.ts`.
- AVD state, `~/.android/avd/` — driven by `/ace:mobile-bootstrap` (mobile work only).

**Single check that surfaces what's missing:** `/ace:doctor`'s `[Auth liveness]` block runs one live HTTP call per MCP and names the exact remediation command per failure. Run first when picking up work on a new machine.

## Gotchas

**How to maintain this section — it is not an incident log.** This file is read at the start of every session in every repo with ACE installed, so every paragraph here spends attention that the *next* reader needs for something else. It grew 1,858 → 5,897 words between 2026-04-27 and 2026-07-23, monotonically. The rule (the same one canopy's operating model states as "invariants are hooks, not memory — prose relies on the model choosing to comply, which fails under load"):

- **A gotcha with an enforcing test, probe, or hook gets ONE line naming the enforcement** — not a postmortem. The test is the invariant; the paragraph is a duplicate competing for attention with the rules that have no enforcement. Link the deeper story to `docs/learnings/` or the issue.
- **A gotcha with NO enforcement is a missing preventer, not a permanent entry.** Either write the preventer, or file it labelled `harness` and leave the one-liner until it lands.
- **Un-testable external knowledge stays in full** — how CommCare HQ, Connect, Nova, Drive, or OCS actually behave. That's the class that genuinely can't be a test, and it's what this section is *for*.
- **When you add one, check whether it belongs in a per-integration playbook instead** (`playbook/integrations/*.md`). Surface-specific mechanics belong there; only cross-cutting traps belong here.

- **`.gws-sa-key.json` and `.env` are per-machine and gitignored.** At `${CLAUDE_PLUGIN_DATA}/`. To inspect env state, read `${CLAUDE_PLUGIN_DATA}/.env` directly — values are loaded into MCP subprocesses, not the parent shell, so `$ACE_*` in your shell will normally be empty.
- **Raw `adb` must target the mobile MCP's own adb server, and that port is ALLOCATED, not fixed — ask `mobile_diagnose`, never assume a number.** Any other port reports an empty device list while the emulator runs fine, which reads as a dead device. `mcp/mobile/port-allocator.ts` starts at `DEFAULT_ADB_PORT = 5037` and walks upward binding a real `net.Server` until it finds a free pair, so two concurrent runs don't collide — a live run has been observed on 5038. (This line used to name 5039 as *the* port; that was one observation written down as a constant, and it cost a session two wrong readings, including calling a healthy booted emulator a zombie.) *Enforced:* `mobile_diagnose` works on the local backend and reports the port + serial in use (`test/mcp/mobile/local-diagnose.test.ts`) — that is the answer, not a remembered number. To find it by hand, **ask the OS which adb servers are actually listening — never probe with `adb`**: `lsof -nP -iTCP -sTCP:LISTEN | awk '$1 ~ /^adb/ {print $9}'`. A port-scanning loop (`ANDROID_ADB_SERVER_PORT=$p adb devices`) is wrong twice over: `adb` **starts a daemon** on any port that has none, so the scan manufactures the servers it then reports, and every fresh daemon discovers the same emulator by scanning 5554+ — so it prints a hit on every port you probed and tells you nothing. Measured: one such sweep spawned three stray daemons and reported the emulator on four ports.

- **`update_yaml_file` `two-level` merge replaces a phase child WHOLESALE — use `deep` for nested patches.** `two-level` only protects top-level-key *children*; a partial patch of `phases.<phase>` (e.g. just `{status}`, just one step under `steps`, or just `products`) **silently drops the rest of that phase block** (the lost-update footgun). When patching a nested path without resending the entire phase block, pass `merge: 'deep'` (recursive, preserves sibling **object keys** at every depth — added after bednet-spot-check/20260529-1124 corrupted `phases.commcare-setup` + `phases.connect-setup` this way; see jjackson/ace#572). **ARRAYS ARE THE EXCEPTION, AND IT BITES: every mode — `deep` included — REPLACES an array wholesale.** Recursion only fires when the value is a plain object on both sides (`mcp/google-drive-server.ts` `deepMerge`), so a partial patch of an array-valued key like `phases.<phase>.residuals` silently discards every element you did not resend. Three successive `deep` patches of the same list leave only the last. To change one element: read the list, build the whole intended array, write it once. *Enforced:* `test/mcp/gdrive/update-yaml-file.test.ts` pins the semantics, including the residuals-shaped repro (ace#1467). Only use `two-level` when you resend the phase's COMPLETE child block.

- **Connect's Learn `passing_score` lives on the shared `CommCareApp` row, not on the opportunity — and a CREATE against an existing row silently DISCARDS the posted value.** `get_or_create(cc_app_id, cc_domain, organization, hq_server, defaults=...)` with `update_existing=False` on the create path (`commcare_connect/opportunity/forms.py:556-587`), so the row is keyed on the app: every opp in the org wired to the same HQ Learn app reads one score, and changing it for one changes the gate for all.
